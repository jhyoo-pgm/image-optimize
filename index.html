이미지 최적화 데모

같은 이미지를 포맷(JPG / WebP / AVIF) × 해상도(800w / 1600w / 2400w)로 만들어 비교합니다.
브라우저 개발자도구 → Network 탭과 함께 보세요.

화면 DPR: - 뷰포트 너비: -px

1. 포맷 비교 — 같은 픽셀, 다른 용량

모두 1600px 폭의 동일한 원본을 포맷만 바꿔 저장했습니다. 화면에는 같은 크기로 표시되지만 다운로드 용량과 속도는 크게 다릅니다.

인코딩 품질: JPG quality 80 (mozjpeg) · WebP quality 80 · AVIF quality 50 ※ 품질 수치는 포맷마다 알고리즘이 달라 직접 비교는 무의미합니다. WebP/AVIF는 같은 수치에서 JPG보다 더 작으면서 더 깨끗합니다. WebP는 75~85가 일반적인 권장 범위(Google), AVIF는 50 전후가 "시각적 손실 없음"의 기준선입니다.

💡 어떤 포맷을 써야 할까?
  • AVIF: 가장 작지만 인코딩이 느리고 일부 구형 브라우저 미지원.
  • WebP: 지원 범위 넓음(IE 제외 사실상 전부). 현재 가장 안전한 기본값.
  • JPG: 폴백(fallback)용. <picture> 로 함께 제공하면 자동 선택됩니다. 
<picture>
  <source srcset="hero.avif" type="image/avif" />
  <source srcset="hero.webp" type="image/webp" />
  <img src="hero.jpg" alt="" />
</picture>

2. 왜 화면 크기보다 2~3배 큰 이미지를 넣을까?

아래 슬롯은 모두 CSS 너비 800px로 고정되어 있습니다. 슬롯 자체는 동일하고, 그 안에 들어가는 이미지의 원본 해상도만 800w / 1600w / 2400w로 다릅니다. 현재 화면의 devicePixelRatio = - 기준으로 보면, 800px CSS 슬롯의 실제 픽셀 폭은 -px 입니다. 이 픽셀 수를 채우지 못하는 이미지는 흐릿해 보입니다.

↑ 이미지 위에 마우스를 올리면 같은 비율(2.5배)로 확대됩니다. 확대하면 1x 이미지의 부족한 픽셀이 늘어나며 흐릿해지고, 2x는 비교적 또렷하게 유지되는 차이를 볼 수 있습니다. 화면이 800px보다 좁으면 슬롯이 자동으로 축소됩니다.

💡 그래서 "레티나 대응 = 3x까지"라는 말이 나오는 겁니다

DPR(devicePixelRatio)별 디바이스 분포 (2024 기준)

  • DPR 1: 일반 데스크톱 모니터, 저가형 노트북. 여전히 무시할 수 없는 비중 (특히 B2B).
  • DPR 2: 맥북·아이맥, iPhone SE/일반 모델, 대부분의 안드로이드 중급기. 가장 큰 사용자 그룹.
  • DPR 3: iPhone Pro/Pro Max/Plus, 갤럭시 S/노트 플래그십. 모바일 트래픽이 많은 서비스라면 무시 못함.

3x까지 준비하는 게 가치 있는 경우

  • 모바일 사용자 비중이 높은 서비스 — 커머스, 미디어, 소셜.
  • 디테일이 중요한 이미지 — 브랜드 히어로 배너, 제품 컷, 로고/일러스트, 텍스트가 포함된 이미지.
  • 첫 화면(Above the fold)의 LCP 이미지 — 사용자 인상을 좌우하는 핵심 이미지.

3x가 과한 경우

  • 본문 안의 일반 사진, 썸네일, 장식용 배경 이미지 — 2x로 충분.
  • 데이터 절약이 우선인 페이지 (느린 네트워크 대상).
  • 표시 크기 자체가 작은 경우 (예: 200px 폭 아바타) — 2x 기준 400w면 충분.

💡 안전한 기본 전략: srcset에 1x, 2x, 3x를 모두 등록하고 sizes로 표시 크기를 알려주면, 브라우저가 디바이스 DPR과 네트워크 상태를 종합해 가장 적합한 하나만 다운로드합니다. 3x를 추가해도 DPR 2 사용자는 여전히 2x 파일만 받습니다.

💡 그래서 실무에서는 srcset을 씁니다

브라우저가 디바이스 DPR과 표시 크기에 따라 가장 적합한 이미지를 자동 선택하도록 만드는 표준 방법입니다. 

<img
  src="hero-800w.webp"
  srcset="
    hero-800w.webp   800w,
    hero-1600w.webp 1600w,
    hero-2400w.webp 2400w"
  sizes="(max-width: 768px) 100vw, 800px"
  alt=""
/>

이 페이지에서는 비교 시연을 위해 일부러 고정 소스를 사용했지만, 실제 서비스에서는 위 패턴이 정답입니다.

3. 로딩 체감 — 9개 변형 동시 로드

모든 변형을 동시에 새로 받아와 다운로드 시간과 용량을 표시합니다. 개발자도구 Network 탭에서 Slow 4G로 throttling을 걸어 다시 측정해보면 차이가 더 극적으로 드러납니다.

파일 포맷 해상도 용량 로드 시간 전송 속도(추정)

※ 로드 시간은 브라우저·네트워크 상태에 따라 매번 달라집니다. 캐시가 있으면 0~수 ms로 찍힐 수 있어요. "캐시 무시하고 다시 측정" 버튼으로 매번 새로 받아옵니다.

핵심 요약

  1. 포맷: WebP/AVIF가 같은 화질에서 30~70% 더 가볍습니다. <picture>로 폴백을 함께 제공하세요.
  2. 해상도: 표시 크기의 2배(보통 2x)를 기준으로 준비하고, srcset으로 디바이스가 알아서 고르게 합니다. 3x는 보통 과합니다.
  3. 용량 = 시간: 모바일·해외 사용자에게는 100KB 차이도 체감됩니다. LCP 점수에 직결됩니다.
  4. 지연 로딩: 화면 밖 이미지는 loading="lazy"로. 첫 화면(LCP) 이미지는 fetchpriority="high"로.
